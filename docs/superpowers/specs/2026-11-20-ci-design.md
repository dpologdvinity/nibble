# CI and automation: design

Date: 2026-11-20. Status: requirements agreed in conversation (the owner then handed the remaining calls to the
builder); calls made by the builder are marked *(builder's call)*.

## Intent

nibble's CI should show an engineer who opens the repository (a recruiter forwards it; an engineer judges it) that
the project is engineered with unusual rigor: checks that run around the clock, bots that report on every pull request
in nibble's own terms (speed, accuracy against llama.cpp, size), agents that work alongside the owner, and a signed,
attested release. The results must be visible without reading YAML: badges, a "How nibble is tested" section in the
README, and a public dashboard.

The governing rule, agreed with the owner: **every workflow has a reason to exist that an engineer can see**. Nothing
is added to raise a count.

## Goals

1. Continuous verification beyond the per-PR suite: nightly accuracy against llama.cpp on real models, long-running
   fuzzing with a persistent corpus, sanitizers on real models, and a weekly portability sweep (ARM64, newest
   compilers).
2. A single bot comment on each pull request with the change's effect on decode/prefill speed, binary size, peak
   memory and accuracy.
3. Proof, in CI, that a bug-fix pull request carries a test that fails without the fix (AGENTS.md already requires
   this; CI currently trusts it).
4. An agent loop: a nightly failure opens an issue; Claude diagnoses it and opens a pull request with the failing test
   as its first commit and the fix as the next; the owner reviews and merges. `@claude` works on issues and PRs, and
   PRs get an automatic Claude review.
5. Supply-chain hardening: CodeQL (C++ and workflows), OpenSSF Scorecard, gitleaks in CI, build-provenance and SBOM
   attestations for release tarballs and the container image, workflow linting.
6. Visibility: badges backed by real data, a GitHub Pages dashboard with history charts, a README section that explains
   the system, CHANGELOG.md, and the repository settings `~/git/AGENTS/SETUP.md` asks for (description, topics, area
   labels, issue templates).

## Non-goals

- Changing nibble's numerics, kernels or CLI behavior (except small, test-backed fixes the new checks uncover, each in
  its own PR).
- Moving the README benchmark tables to CI: they stay tool-generated on an idle dedicated machine
  (`tools/bench_final.sh`). CI runner numbers are trend data only and are labelled so everywhere.
- Supporting Windows or macOS builds.
- Deploying anything other than the Pages dashboard and the existing release artifacts.

## Anti-goals (failure even if it works)

- A workflow without a stated, visible reason; copying daydaze's workflows because they exist there (screenshots,
  recordings, branch pruning and the like have no nibble counterpart).
- An agent merging its own change. Agent PRs are never auto-merged.
- Strangers spending the owner's Claude subscription: agent workflows run only for the owner (and collaborators).
- PR code running with a write token or secrets (fork PRs in particular).
- Hiding red: nightly status badges show the real state. The owner accepted that a badge is sometimes red.
- Flaky checks becoming required: nothing new joins branch protection until it has been green and stable.
- Slower PR feedback: anything slow runs on a schedule, not on every push.

## Constraints

- The repository is public, so Actions minutes on standard runners (including `ubuntu-24.04-arm`) are free. Hosted
  runners: 4 vCPU, 16 GB RAM, about 14 GB free disk, 6 h per job.
- Existing conventions hold: actions pinned by commit SHA with the tag in a comment (Dependabot keeps them current);
  least-privilege `permissions:` per workflow and job; every workflow file opens with a comment saying why it exists
  and how to run it by hand; Conventional Commits; `master` is protected (10 required checks, admins included), so
  every change lands through a PR.
- Logic does not live in YAML. Anything beyond a few lines of shell goes into typed, tested Python under `tools/ci/`
  (ruff, ruff format and `mypy --strict` already cover `tools/`; unit tests run in the `lint` job beside the `bench/`
  tests) or into shellcheck-clean scripts. YAML stays thin glue *(builder's call)*.
- Model files and goldens are never committed. CI downloads them and caches them by key.
- Secrets: the agent workflows need `CLAUDE_CODE_OAUTH_TOKEN` (the owner's subscription, as in daydaze). Everything
  else uses `GITHUB_TOKEN`. Every workflow must degrade cleanly (skip, with a notice in the job summary) when a
  secret is absent: forks, Dependabot.
- Owner-only steps (secret, enabling Pages, social preview image, Claude GitHub App) go in the git-excluded owner
  ledger, `STEPS-FOR-OWNER.md` at the repository root (it already exists there and is excluded through
  `.git/info/exclude`).

## Design

### Shared building blocks

- **`.github/actions/setup-models`** (composite action): downloads Qwen2.5-0.5B-Instruct (F16, from the source
  `tools/download_models.sh` already uses), builds the pinned llama.cpp (`tools/build_llama_cpp.sh`, both the native
  and `--generic` builds), makes the quantized files (`tools/make_quants.sh`) and the goldens (`tools/make_golden.sh`),
  all behind `actions/cache` keyed on `tools/llama_cpp_version.txt` and the hashes of those scripts. A cache hit costs
  a restore; a miss rebuilds everything (about 1 to 2 hours, inside one job's limit). Llama 3.2 needs a gated Hugging
  Face download and stays local-only; TinyLlama is added if the converter's dependencies fit the runner, otherwise it
  stays local-only too *(builder's call)*.
- **`.github/actions/report-failure`** (composite action, logic in `tools/ci/report_failure.py`): for a scheduled job
  that fails, opens one issue per job (title `nightly: <job> failing`, labels `ci-failure` plus an area label), or
  comments on the open one; includes the run link, the first failing commit and the last green one, and attaches the
  reproducer (a fuzz crash file, the failing test name). When the job is green again it comments and closes the
  issue. One issue per job, never one per run.
- **`tools/ci/`**: a typed Python package with unit tests for every piece of logic below (statistics for the perf
  comparison, rendering the PR comment, choosing the tests for the bug-fix proof, appending dashboard data, issue
  reporting). Tests are hermetic: no network, no `gh` calls (those go behind a small interface the tests fake).

### Per pull request (fast)

1. **`ci.yml`** (existing) stays the required gate. Additions: the `tools/ci/` unit tests in `lint`, and actionlint
   (below). The current matrix already runs the documented compiler floor (the runner's default g++ 13 and clang 18),
   so a separate "minimum compiler" job is not needed. The README states that CI checks this floor.
2. **`actionlint.yml`**: lints every workflow (syntax, expressions, shellcheck on `run:` blocks) when a workflow or
   action changes. Reason: with many workflows, a typo would silently stop one from running.
3. **`codeql.yml`**: CodeQL for C++ (a manual build, so it sees the tier sources) and for the workflow files, on PRs,
   pushes to `master` and weekly. Reason: nibble parses untrusted GGUF files. Findings go to the Security tab.
4. **`gitleaks.yml`**: secret scan on every push and PR, plus the full history weekly. Reason: the pre-commit hook is
   optional (`lefthook install`), and push protection only covers known provider patterns.
5. **`pr-report.yml`**: one sticky comment per PR, updated on each push:
   - **Speed**: base and head are built on the same runner and benchmarked in an interleaved ABBA order (the
     protocol `tools/bench_final.sh --abba` uses) with `nibble bench` on Qwen2.5-0.5B Q4_0 and Q8_0, one thread and
     all runner threads. The comment reports the median ratio and its spread per row, and says when the spread is
     too wide to call. Labelled "shared CI runner: trend, not a benchmark".
   - **Size**: the size of the `nibble` binary, base to head.
   - **Memory**: peak RSS for a fixed generation, base to head.
   - **Accuracy**: if the goldens cache is warm, the Qwen2.5-0.5B end-to-end tests run on head, and the comment shows
     their `min cosine` lines next to base's. When kernels that must be bit-identical change, any difference is
     flagged. If the cache is cold, the comment says it was skipped.
   - Runs only when `src/`, `include/`, `cli/`, `CMakeLists.txt` or `tests/` change. The job that runs PR code has
     a read-only token. A separate `workflow_run` job, which never checks out PR code, posts the comment from the
     uploaded artifact, so fork PRs get it too and cannot misuse the write token.
6. **`fix-proof.yml`**, the bug-fix proof: for a PR whose title or commits are `fix:`/`fix(...)` and which touches
   `src/`, `include/` or `cli/`, CI finds the Catch2 `TEST_CASE`s the PR adds or changes. It builds the merge base
   with the PR's `tests/` applied and runs those cases. They must fail there and pass on head (head already runs in
   `ci.yml`).
   - Outcomes, written to the job summary: **proven** (fails on base, passes on head); **no test** (fails; a
     `no-test-needed` label with a stated reason in the PR overrides it); **does not reproduce** (passes on base:
     fails the check); **base does not compile with the new test** (reported as proven with a note, because the
     test depends on the fix's interface).
   - Not required at first.

### Scheduled (around the clock)

7. **`nightly.yml`** (daily on `master`, and by hand). Each job reports failures through `report-failure`:
   - **accuracy**: `setup-models`, then `ctest -L e2e` on the Qwen2.5-0.5B family (F16, Q8_0, Q4_0, Q4_K_M,
     Q5_K_M, Q6_K). The `min cosine` lines are recorded to the dashboard data, and any change from the previous
     night is flagged in the summary.
   - **sanitizers on real models**: ASan+UBSan build, end-to-end tests on Qwen2.5-0.5B Q4_K_M. Reason: the per-PR
     sanitizer jobs only see the tiny synthetic models.
   - **fuzz**: `fuzz_gguf` and `fuzz_load` for about 2 h each (in parallel jobs). The corpus persists between nights
     in the cache, minimized with `-merge=1` before saving. A crash uploads the reproducer and opens an issue with
     it. Cumulative fuzzing hours are recorded to the dashboard.
   - **trend benchmark**: `nibble bench` on `master`'s head (Qwen Q4_0/Q8_0, 1 and all threads), appended to the
     dashboard data.
8. **`portability.yml`** (weekly, and by hand):
   - **ARM64** on `ubuntu-24.04-arm`: scalar build and the full non-e2e suite. If this exposes x86-only code, the fix
     is its own PR, and the README platform badge then gains linux-arm64.
   - **Newest GCC and Clang** (latest packaged releases, e.g. from the LLVM apt repository) with `-Werror`, to catch
     new warnings before the runner image moves.
   - **Configurations not in the PR matrix**: `-DNIBBLE_SIMD=OFF` with `-DNIBBLE_NATIVE=OFF`, and a Release build
     with `-O3` plus LTO *(builder's call: only if the build supports LTO without changes)*.
9. **`scorecard.yml`**: OpenSSF Scorecard weekly and on pushes to `master`, publishing results (README badge) and
   SARIF to the Security tab.
10. **`link-check.yml`**: lychee weekly over README, ARCHITECTURE, CONTRIBUTING, SECURITY and `docs/`, keeping one
    open issue updated with the broken links.

### Release

11. **`release.yml` / `package.yml`**:
    - Build-provenance attestations (`actions/attest-build-provenance`) for the tarballs and the ghcr.io image, and an
      SPDX SBOM per artifact, attested and attached to the draft release. The README shows how to verify with
      `gh attestation verify`.
    - Release notes come from the Conventional Commits since the previous tag (git-cliff, configured in the repo) and
      prepend a section to `CHANGELOG.md`. CHANGELOG.md is backfilled once from the existing tags (v0.7.0, v0.7.1,
      v0.8.0 and earlier).

### Agents

12. **`claude.yml`**: `@claude` in an issue, a PR comment or a review runs Claude Code (`anthropics/claude-code-action`)
    with `CLAUDE_CODE_OAUTH_TOKEN`. It runs only when the commenter's association is OWNER, MEMBER or COLLABORATOR.
    Claude follows AGENTS.md (it reads it from the repo).
13. **`claude-review.yml`**: an automatic Claude review on non-draft PRs opened by the owner, Dependabot or the agent,
    once per push. It posts review comments only (no approval, no changes), focusing on numerics, the no-allocation
    rule on the decode path, bit-identity, and AGENTS.md conventions.
14. **`claude-triage.yml`**: when an issue gets the `ci-failure` label:
    - Claude comments a diagnosis: the suspect commits between the last green and first red run, and why.
    - When it has a reproducer, Claude opens a PR from an `agent/` branch: commit 1 adds the failing test, commit 2
      fixes it. The PR has the `agent` label and links the issue. `fix-proof.yml` then proves the test independently.
    - It never merges. If the diagnosis is not confident, it says so and stops at the comment.
15. **`automerge.yml`**: enables auto-merge on Dependabot's grouped minor/patch PRs and on the owner's PRs that are
    not drafts, so they merge when the required checks pass. Never on `agent`-labelled PRs. This requires the
    repository's *Allow auto-merge* setting (currently off; the builder turns it on with `gh api`).
16. **`labeler.yml`**: labels PRs by area from changed paths: `kernels`, `gguf`, `tokenizer`, `model`, `cli`,
    `build`, `ci`, `docs`, `bench`. Reason: the changelog and the dashboard group by area, and triage issues get the
    same labels.

### Dashboard (GitHub Pages)

17. **`dashboard.yml`** (after each nightly, and by hand):
    - Data lives as JSONL on a `dashboard-data` branch: one row per nightly per metric, with commit, date and runner
      CPU model.
    - A static site goes to Pages, rendered by Python. Charts are SVGs from `bench/plot.py` (extended as needed),
      so there is no JavaScript framework *(builder's call)*.
    - Pages: decode/prefill tokens/s over time (trend, CI runner); min cosine per quant type over time; cumulative
      fuzzing hours and corpus size; binary size; line coverage (from the coverage job's summary on `master`); and the
      latest status of every scheduled job.
    - The README links it, and a nightly badge points at it.

### Repository presentation

18. README:
    - A "How nibble is tested" section: a short table of each workflow, what it protects and how often it runs, plus
      a small flow diagram (Mermaid, which GitHub renders) of the nightly → issue → agent → PR → owner loop.
    - Badges: keep the current ones that are backed by data. Add nightly status, CodeQL, OpenSSF Scorecard, latest
      release, and the dashboard. Remove any that break.
19. CONTRIBUTING.md and ARCHITECTURE.md describe the new workflows, `tools/ci/`, and how to run each workflow by
    hand. AGENTS.md mentions the `agent/` branch and label convention.
20. Repository settings per `~/git/AGENTS/SETUP.md`:
    - The About description and topics (e.g. `llm`, `inference`, `cpp20`, `gguf`, `simd`, `quantization`, `avx2`,
      `llama-cpp`).
    - Area labels plus `ci-failure`, `agent`, `no-test-needed`.
    - `.github/ISSUE_TEMPLATE/` (bug report, feature request) and a `config.yml` pointing security reports at
      SECURITY.md.

## Rollout

Each item above lands as its own PR (or a few related ones), in this order:

1. Foundations: `tools/ci/` skeleton, labeler and labels, issue templates, repository settings, actionlint.
2. Security: CodeQL, gitleaks, Scorecard.
3. Nightly: `setup-models`, `report-failure`, then the accuracy, sanitizer, fuzz and trend jobs; portability.
4. Per-PR: `pr-report`, `fix-proof`.
5. Dashboard.
6. Agents: claude, claude-review, claude-triage, automerge (after the owner adds the secret; until then they skip).
7. Release: attestations, SBOM, CHANGELOG and git-cliff.
8. Docs and badges, last, describing what actually exists.

New checks become required only after about two weeks of stable green. That decision is the owner's, recorded in the
owner ledger.

## Success criteria

- Every new workflow file starts with a comment giving its reason and how to run it by hand; actionlint passes on all
  of them.
- Each scheduled workflow has run green at least once on `master` (or red with a real finding, triaged).
- A demonstration: a deliberately broken commit on a throwaway branch makes `fix-proof` report "does not reproduce",
  and a real fixture of a fix with its test reports "proven". The PR report comment appears on a PR touching `src/`.
- The dashboard is live on Pages with at least one data point per chart.
- `tools/ci/` is covered by unit tests run in CI; ruff, ruff format and mypy strict pass.
- The README "How nibble is tested" section and badges match what exists. No badge points at missing data.

## Left to the builder

- Exact cron times (spread out, off the hour), timeouts, artifact retention, cache keys.
- Third-party actions to use, provided they are well maintained and SHA-pinned.
- The dashboard's layout and styling.
- Whether TinyLlama joins the nightly accuracy job.
- How `fix-proof` maps changed lines to `TEST_CASE` names: parsing is enough, and it must have unit tests for its
  edge cases (renamed cases, sections, tags).
