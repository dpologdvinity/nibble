# nibble M7 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Load and run the GGUF mixes people actually download, `Q4_K_M`, `Q5_K_M` and `Q6_K` from plain `llama-quantize` (not `--pure`), on Qwen2.5-0.5B-Instruct, Llama-3.2-1B-Instruct and TinyLlama-1.1B-Chat. Every new kernel must be bit-exact with ggml's generic reference: the activation quantizers, dequantization and block dots. This is spec roadmap v1.1 (spec §1 line 37, §9 line 264), widened to the types those mixes really contain.

**Architecture:** M4's shape stays. Each weight type has a scalar dequant and a scalar block dot against its ggml `vec_dot_type` activation block, pinned by golden vectors from ggml's generic code (`tools/quant_vectors`). The CPU backend quantizes each matmul input once per activation type it needs, into scratch sized at `reserve()`. The AVX2 twins are bit-identical to the scalar code. All weights share the existing per-weight row and GEMM dispatch in `matmul_multi`.

**Tech Stack:** unchanged (C++20, g++ 13 / clang 18, CMake, Catch2 v3.16.1, x86 intrinsics). llama.cpp b11715 (`tools/llama_cpp_version.txt`): `third_party/build` for `llama-quantize` and `llama-bench`, `third_party/build-generic` for goldens and golden vectors.

**Spec:** `docs/superpowers/specs/2026-10-17-nibble-design.md` (§1 lines 33/37, §5.1 quantized matmul, §9 line 264). Earlier plans: `2026-10-17-nibble-m4.md` (bit-exact Q8_0/Q4_0 recipe), `2026-10-19-nibble-m6.md` (SIMD, bench protocol).

**Reference algorithms and float order.** Line numbers are in `ggml/src/ggml-quants.c` (Q) and `ggml/src/ggml-cpu/quants.c` (C). Every `int × float` converts the int to float first. With no FMA in the generic build, nothing is contracted.
- `nearest_int` (Q `:621-626`) is `memcpy` bits of `fval + 12582912.f`, then `(i & 0x7fffff) - 0x400000`. That is round-half-to-even, unlike Q8_0's `roundf`.
- `quantize_row_q8_K_ref` (Q `:2769-2805`), per 256 elements:
  - Scan j ascending. Set `amax = |x[j]|, max = x[j]` only when `|x[j]| > amax`, so the first maximum wins and the sign is kept.
  - If `amax == 0`: `d = 0` and `qs = 0`. **`bsums` is not written.**
  - Otherwise `iscale = -127.f/max` and `qs[j] = MIN(127, nearest_int(iscale*x[j]))`.
  - `bsums[g]` = int sum of the 16 `qs` in group g.
  - `d = 1/iscale`, a float that is negative when `max > 0`.
- `quantize_row_q8_1_ref` (Q `:302-334`): `amax`, `d = amax/127`, `id = d ? 1/d : 0` and `qs = roundf(x*id)` match Q8_0. `d` is stored as fp16. Then `s = fp16(float(sum) * d)`, which uses the **unrounded float** `d`.
- Dequantization:
  - `dequantize_row_q5_0` (Q `:500-524`): `((qs&0xF) | ((qh>>j)<<4 & 0x10)) - 16`. Element j+16 takes its high bit from `qh` bit j+16. `y = x0*d`.
  - `dequantize_row_q5_1` (Q `:526-550`): unsigned 5-bit value, `y = x0*d + m`.
  - `get_scale_min_k4` (Q `:880-887`): for j < 4, `sc = q[j]&63`, `m = q[j+4]&63`. Otherwise `sc = (q[j+4]&0xF) | ((q[j-4]>>6)<<4)` and `m = (q[j+4]>>4) | ((q[j]>>6)<<4)`.
  - `dequantize_row_q4_K` (Q `:1530-1552`): per 64 elements, `d1 = d*sc`, `m1 = dmin*m`, `y = d1*q - m1`. The low nibbles of `qs[32·k..]` are sub-block 2k and the high nibbles are sub-block 2k+1.
  - `dequantize_row_q5_K` (Q `:1732-1756`): the same, plus 16 when `qh[l]` bit 2k (low) or 2k+1 (high) is set.
  - `dequantize_row_q6_K` (Q `:1940-1966`): `y = (d*sc)*q`, where `q = (ql nibble | 2 bits of qh << 4) - 32` and the scale index is element/16.
- Dots:
  - `ggml_vec_dot_q5_0_q8_0_generic` (C `:365-406`): exact integer block sum, then `sumf += (dx*dy) * sumi`.
  - `ggml_vec_dot_q5_1_q8_1_generic` (C `:408-450`): `sumf += ((dx*dy)*sumi + mx*sy)`. The two products are added first, then the result goes into `sumf`.
  - `ggml_vec_dot_q{4,5}_K_q8_K_generic` (C `:696-769`, `:771-849`), per super-block i:
    - Integer `aux32[l]` for l = 0..7 sums `scale(e/32) * q8[e] * a[e]` over the elements e with **e mod 8 == l**.
    - Integer `sumi = Σ_g bsums[g] * min(g/2)`.
    - `d = fp16(x.d) * y.d`, then `sums[l] += d * aux32[l]` for each l (8 float accumulators that live across super-blocks).
    - `dmin = fp16(x.dmin) * y.d`, then `sumf -= dmin * sumi`.
    - After the last block: `sumf += sums[0]`, then `sums[1]`, through `sums[7]`, in order.
  - `ggml_vec_dot_q6_K_q8_K_generic` (C `:851-918`): the same lane structure, with `scale = int8 scales[e/16]`, no min term, and the same final order.
  - The ggml-quants.c `get_scale_min_k4` and the dots' `utmp`/`kmask` unpacking decode to the same (scale, min) pairs.

## Decisions this plan makes (for review)

1. **Dtype set = exactly what the nine files use.** New weight types are Q5_0 (6), Q5_1 (7), Q4_K (12), Q5_K (13) and Q6_K (14), added to F32/F16/Q4_0/Q8_0. Q2_K, Q3_K, Q4_1, IQ types, BF16 and Q8_K-as-a-file-tensor stay rejected. This is wider than the spec's "Q4_K and Q6_K" because Qwen's 896-wide rows and Q5_K_M cannot load without Q5_0, Q5_1 and Q5_K. The spec is not edited (it is under `docs/superpowers/`). The README records the actual set.
2. **Activation types follow ggml's `vec_dot_type`:**
   - Q8_0 for Q4_0, Q5_0 and Q8_0
   - Q8_1 for Q5_1
   - Q8_K for Q4_K, Q5_K and Q6_K
   
   Q8_1 is a separate quantizer. Its `s` uses the pre-fp16 `d`, so it cannot be derived from a Q8_0 block. The Q8_1 and Q8_K quantizers stay **scalar**. They are O(n·width) per matmul against the matmul's O(n·width·rows). Task 7's bench is the check.
3. **Bit-exactness definition:**
   - Scalar dequantization, the quantizers and the dots equal ggml's generic functions bit for bit on the golden vectors.
   - The AVX2 dots equal the scalar dots bit for bit on all finite inputs, for any row range, n, or thread count.
   - Inputs containing NaN or Inf have no exactness requirement but must not crash or trigger UB.
   - The integer lane structure of the K-quant dots (aux32 by element mod 8) and the final `sums[0..7]` order are part of the contract.
4. **Gate unchanged:** the quantized gate, cosine ≥ 0.995 at every position and on the prefill last row, ≥ 90% top-1 agreement with near-ties (top-2 gap < 1e-3) counting as agreement, greedy reported only. The comparison is against `build-generic` llama_ref with `--kv-f32`. **If any K-quant case fails it after the kernels pass their goldens, STOP and ask the user with the measured numbers. Never loosen the gate.**
5. **GEMM:** all new types use the AVX2 row path (4 weight rows share each activation block) for every n. No new tile is required for M7. Q4_0/Q8_0 keep `gemm_q`. Task 6 is an optional, measured Q5_0 and K-quant prefill tile with an explicit trigger.
6. **Integrity checks match the existing policy.** The loader checks shape, block multiple and byte bounds, as it does today. It does not check that fp16 scales are finite (`ggml_validate_row_data`, Q `:5526-5560`, does, but nibble does not do this for Q8_0/Q4_0 either). Every bit pattern of every new block decodes to in-range indices, because all fields are masked. Non-finite scales give NaN logits, not UB. Fuzzing covers this.
7. **matmul_multi takes mixed types.** The fallback condition shrinks from "same type and same ne0" to "same ne0" only. Input is quantized once per distinct activation type, and each weight goes through its own kernel. This is required, not optional: Llama and TinyLlama Q4_K_M mix Q4_K/Q6_K in `attn_v` for half the layers, and Qwen mixes Q5_0/Q8_0 or Q5_1/Q8_0 (two activation types).
8. **README claims:** Q4_K_M / Q5_K_M / Q6_K from plain `llama-quantize` for all three models, with the type list from decision 1. It states the measured min cosine and agreement per file. Other K-quant mixes (Q3_K_*, Q2_K, IQ*) and `--pure` K files with Q4_1 are not claimed.
9. **Performance: report only, no target.** Bench with `tools/bench_final.sh --abba 2` at t = 1, 8 on the three Q4_K_M and three Q6_K files, as Task 7 specifies. Expect K-quant decode to trail llama.cpp's native AVX2. Its kernels sum lanes in an order nibble cannot use while staying bit-exact with generic.

## Review Focus

1. **Malformed K-quant blocks from an untrusted file.** Covers random bytes, all-ones scale bytes (6-bit sc/m = 63; Q6_K scale -128), `qh` all ones, and fp16 NaN/Inf in `d`/`dmin`. Dequant and dots must not show UB or out-of-bounds reads. Scalar and AVX2 must agree bitwise when finite, and both must be NaN when either is. Test: Task 3 `k-quant blocks with any bytes are safe`, Task 5 `simd k-quant dots on hostile blocks`, and Task 4's fuzz seed.
2. **A K-quant tensor whose ne0 is not a multiple of 256** (e.g. Q4_K with ne0 = 896), or Q5_0 with ne0 = 48. The load error must name the tensor, the type and the block size. Test: Task 1 `k-quant ne0 not a multiple of 256 is rejected`.
3. **Mixed-type layers.** Cases: Q/K/V = {Q4_K, Q4_K, Q6_K}; {Q5_1, Q5_1, Q8_0} (two activation types); gate/up of different types. Results must equal separate `matmul` calls bitwise, quantize once per activation type and allocate nothing. Test: Task 4 `matmul_multi with mixed weight types equals separate matmuls` and `alloc: mixed k-quant model`.
4. **SIMD tails.** Row ranges not a multiple of 4 (1, 3, 5, 37), n ∈ {1, 5}, one super-block per row, and odd block sizes (22, 24, 144, 176, 210 bytes), so blocks are unaligned. Test: Task 5 `simd new-type dots and matmul_rows_q equal scalar bitwise`.
5. **Unsupported types** (Q3_K, Q4_1, IQ4_NL, BF16, Q8_K stored in a file). The error must name the type and list the supported set, at `File::parse` and in `nibble info`. Test: Task 1 `gguf unsupported tensor type names the type`, updated and extended.

- `simd::matmul_rows_q` dispatches every type to AVX2, using 4-row variants that share each activation block like `dot4`, plus a 1-row remainder.
- Q5_0 becomes a weight trait in the existing `dot1/dot4/matmul_t` templates:
  - Expand `qh` bits to 0x10 bytes. The values are in [-16, 15], so `mul_sum_i8` is exact.
  - `scale` = `float(s) * (dw*da)`, which is the `Q8` trait's order.
- Q5_1 needs the templates parameterized on the activation block type (stride, `qs` offset 4). Its trait adds `mw*sa` after the product, per the scalar order. The unsigned weights are in [0, 31], so `maddubs` cannot saturate: 2·31·127 < 32767.
- **K-quant integer lanes** must reproduce the generic `aux32[l]`, the sum over elements ≡ l (mod 8). Plain `maddubs`/`madd` on the natural layout mixes lanes and is **not allowed**. Required method:
  - Apply one fixed byte permutation to both the weight bytes and the activation bytes, so int32 lane l holds elements {l, l+8, l+16, l+24} of each 32-element group. That is an in-lane `shuffle_epi8` to pair (k, k+8), plus a 16-bit unpack across halves.
  - Then `maddubs` and `madd_epi16` by the sub-block scale give exactly `scale × Σ` per lane:
    - Q4_K and Q5_K: one scale per 32 elements.
    - Q6_K: scales per 16 elements, so the scale vector alternates (s0, s1) per int16 pair.
    - Q6_K signed weights: use the `mul_sum_i8`-style sign transfer. a is never −128 because Q8_K output is in [−127, 127].
  - Saturation bounds hold: Q4_K 2·15·127, Q5_K 2·31·127 and Q6_K 2·32·127, all < 32767.
  - Add the bounds and the lane rule as one comment.
- K-quant float part:
  - `sums8 = _mm256_add_ps(sums8, _mm256_mul_ps(_mm256_set1_ps(d), _mm256_cvtepi32_ps(acc)))`. No FMA.
  - `sumi` from `bsums × mins` in integers.
  - Scalar `sumf -= dmin*float(sumi)` per super-block.
  - At the end, store `sums8` and add lanes 0..7 to `sumf` **sequentially**, not with an hsum tree.
- No VNNI variant in M7: the bit-exact lane layout is the constraint, not the multiply.
